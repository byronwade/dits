# Long-term product vision

**Maturity:** Design

Long-term strategy, not product availability, customer proof, or a delivery commitment.

> Strategy document, not product status. Last reviewed: 2026-07-16. See
> [`docs/STATUS.md`](../STATUS.md) for what works now and
> [`docs/marketing/positioning.md`](positioning.md) for approved public language.

## The durable thesis

Large creative outputs are usually stored as opaque files even though they are
the result of a structured process: source assets, project files, edit
decisions, dependencies, tools, and renditions. A filename or object hash can
prove which bytes exist; it cannot explain how those bytes came to be.

Dits can become the open history layer for that process:

> Exact source history plus a reproducible graph of edits, dependencies, and
> renditions.

This is ambitious without requiring Dits to become an editor, review suite,
cloud drive, or general-purpose AI platform.

## Product model

The long-term model has four linked records:

1. **Source objects** — immutable, content-addressed bytes.
2. **Edit decisions** — trims, transforms, grades, selections, and other intent
   represented explicitly where a format permits it.
3. **Dependencies** — the project, tool, configuration, and upstream objects
   required to reproduce an output.
4. **Renditions** — proxies, thumbnails, review encodes, and final exports that
   can be traced back to their inputs.

The system should always be able to distinguish an exact archival source from a
derived or approximate representation.

## What “semantic” should mean

Semantic media support is useful only when it creates verifiable behavior. It
should enable questions such as:

- Which source frames and edit decisions produced this rendition?
- Did two branches alter the same intent, or only different derived outputs?
- Can this proxy be regenerated rather than stored forever?
- Which assets are affected if this source or project node changes?

Labels generated by models may enrich this graph, but AI is an optional
consumer and producer of metadata—not the product foundation or a truth oracle.

## Open protocol vision

Collaboration should exchange the same objects and graph rather than introduce
a proprietary cloud-only data model. A stable protocol must specify:

- canonical object identifiers and manifests;
- capability and format negotiation;
- have/want exchange and resumable object transfer;
- full verification before objects become visible;
- atomic, compare-and-swap ref updates;
- authenticated identities, scoped authorization, and expiring lock leases;
- recovery behavior under interruption and partial failure.

HTTP is the first sensible transport. Bundles, QUIC, or peer transports can be
added later if they preserve identical semantics and pass the same conformance
suite.

## Strategic sequence

1. Prove local data safety and format determinism.
2. Freeze and document the object and manifest format.
3. Demonstrate useful semantic media workflows on real fixtures.
4. Specify and validate a transport-independent remote protocol.
5. Build team UX, policy, review integrations, and hosted operations.
6. Invite independent implementations after the protocol is stable enough to
   deserve them.

## Boundaries

Dits should resist attractive but distracting expansions until the core model
is proven:

- no broad “creative operating system” claim;
- no generic AI assistant;
- no universal editor or automatic lossless converter claim;
- no real-time multi-user editing before safe asynchronous collaboration;
- no P2P-first architecture that treats discovery as authorization;
- no hosted growth strategy before recovery, observability, and protocol
  compatibility are measurable.

## Signs the vision is working

- Users can reproduce outputs from committed source and edit records.
- A change can be explained at the asset or edit-decision level.
- Derived media can be invalidated and regenerated deterministically.
- Independent clients can exchange objects without trusting each other’s
  storage implementation.
- Teams adopt Dits first for the local model, not only because storage is cheap.
