# ADR 0003: Pre-1.0 Repository Compatibility and Manifest Encoding

**Maturity:** Current

Accepted ADRs govern new work, but they do not by themselves prove that every consequence
is implemented; implementation status remains authoritative.

- **Status:** Accepted
- **Date:** 2026-07-16

## Context

Dits 0.1.x writes content-addressed repository objects but has not published a
versioned repository format, migration policy, independent reader, or
conformance corpus. Older documentation described a bincode manifest format and
the reader attempted a bincode fallback, even though the canonical writer has
only emitted JSON manifests. A regression test manufactured a bincode manifest
that no released writer produced.

Treating that manufactured input as a compatibility obligation would preserve
an undocumented Rust-memory-layout dependency and make future independent
implementations harder. Silently changing real repository bytes would be worse.

## Decision

For the pre-1.0 local alpha:

1. Manifest objects are the exact UTF-8 bytes returned by
   `Manifest::to_json()`. Their BLAKE3 digest is their object identity.
2. The manifest reader accepts that JSON representation only. It verifies the
   object digest, parses the schema, validates canonical repository-relative
   paths, and requires each map key to equal the embedded entry path.
3. The removed bincode fallback is not a migration removal: no canonical or
   released Dits manifest writer emitted that representation.
4. The current JSON schema is an implementation format, not a frozen public
   interchange contract. Pre-1.0 repository compatibility is best effort.
5. Any future change that cannot read a repository created by a supported
   release must ship an explicit migration or read-only export path, fixtures
   from the affected release, and a status/release-note update.
6. Before 1.0, Dits must introduce a versioned envelope, resource limits,
   deterministic conformance vectors, corruption cases, and at least one
   independently reproducible reader or verifier.

Users must keep independent backups during the alpha and verify restored bytes.
The CLI must not claim cross-version or third-party compatibility that is not
covered by fixtures.

## Consequences

Positive:

- malformed binary data is not interpreted through an accidental Rust layout;
- manifest identity is deterministic and inspectable;
- path confinement is enforced at the object boundary;
- future format design starts from an explicit compatibility policy.

Costs:

- 0.1.x repositories remain an unstable evaluation format;
- a future envelope or schema may require a migration command;
- JSON is not assumed to be the final space- or decode-efficient encoding.

## Rejected alternatives

### Preserve the undocumented bincode fallback

Rejected because there is no writer, released fixture, version tag, or stable
schema for those bytes. Accepting them would turn Rust serialization details
into an accidental protocol.

### Declare the current JSON schema stable

Rejected until field semantics, bounds, migrations, and cross-implementation
vectors exist.

### Ignore pre-1.0 compatibility entirely

Rejected because even alpha users need a stated backup, export, and migration
expectation.

## Enforcement

- `docs/data-structures/manifest-spec.md` describes the observed current JSON
  contract and its remaining validation gaps.
- Object-store tests cover JSON round trips, non-JSON rejection, digest
  mismatch, path traversal, and key/path mismatch.
- Persistent-format changes follow the repository-wide gate in `AGENTS.md`.
- CI checks product claims and canonical documentation; format changes must add
  cross-version fixtures when a real released writer is affected.
